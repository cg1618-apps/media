# P3b2 — the `nsfw` rule

The second half of P3b. P3b1 (labels and modes in code) has landed; this file
is what remains, and is deleted with P3b2. Spec:
`docs/superpowers/specs/2026-11-03-account-system-design.md`, "Content labels"
(Settled), and "Where the structure differs from today" item 8.

Branch `feat/nsfw-rule`, cut from `dev` after P3b1 merges.


### What is true after it

Every entry or franchise carrying a label other than `nsfw` also carries
`nsfw`, stored. The rule lives in **one function**,
`app/services/domain/label_rules.py`:

```
with_required_labels(keys: set[str]) -> set[str]
refuse_nsfw_removal(old: set[str], new: set[str]) -> None   # 422
```

Every write path goes through it:

| Path | File | Behaviour |
| --- | --- | --- |
| entry and franchise label PUT | `routers/content_labels.py` `_replace_labels` | attaching X adds `nsfw` in the same write; a payload that drops `nsfw` while keeping another label is **422**, and the message names the label that requires it |
| gated auto-label on create and update | `gated_labels.ensure_entry_label` / `ensure_franchise_labels` | adds `nsfw` beside the type's label |
| Pull, after a label tab or gated entry tab | `enforce_gated_label_invariants` (pull.py:2045) | also adds the missing `nsfw` |
| Calculate | `run_sync_gated_labels` | the same |

The SPA picker (`ContentLabelPicker.jsx`): ticking any label ticks NSFW, and
NSFW is disabled while another label is ticked, with a tooltip generated
from the rule (spec: "who sees a label is not written in prose").

### Migration `n1s2fwrule34`, parented on `l1a2belcode3`

Backfill: insert `nsfw` for every `media_id` and `franchise_id` carrying a
non-`nsfw` label without it, at `position = max+1`. Log counts. Spec counts on
company: 134 `h-comic`, 59 `h-game`, 10 `hentai` entries lacked `nsfw`;
re-count at execution.

Visible change: none. `nsfw`'s lowest mode is `normal`, and every other label
is already hidden at or above it.

Downgrade: no-op, documented. The rows it added are indistinguishable from
ones an admin attached, so removing them would guess. Not `irreversible`
either: the schema is unchanged, so a downgrade past it is safe.
